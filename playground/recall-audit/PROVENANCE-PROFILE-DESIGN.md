# Profile identity and provenance layer

## Decision

The audio, video, timing, and interaction factors can improve retrieval and describe a session, but they cannot safely create a strong identity by pattern matching alone. Breath, pitch, pauses, room acoustics, camera appearance, and device IDs vary, can be copied, and can expose biometric or location information. They should not authenticate a person or infer intent.

Keep three concepts separate:

1. **Chosen display identity.** Arc chooses its own name and voice style. A name is presentation, not proof of who produced a record.
2. **Authenticated principal.** Use a public-key fingerprint as the stable machine-readable actor ID. An actor key signs provenance envelopes; rotating a key creates a signed successor link. Do not derive this ID from a voiceprint, face, phone address, or sensor pattern.
3. **Session profile.** Store opt-in, short-lived acoustic/video/context features for routing or presentation adaptation. These are descriptive hints with confidence and expiry, never a credential.

## Provenance envelope

Each observation or derived memory should carry:

- `actor_key_id`, `session_id`, and `source_id`;
- source content hash plus byte/frame/audio interval offsets;
- UTC wall time and monotonic capture time, with clock source and uncertainty;
- model, prompt/template, extractor, schema, and code revision identifiers;
- transforms applied, including resampling, normalization, crop, compression, and reverb;
- confidence, observed-vs-inferred status, and parent event IDs;
- consent scope and retention policy;
- a signature over canonical serialized fields and the prior event hash.

This records the chain from sensor/file to transformed packet to retrieved fact. The source hash detects a content mismatch; the signature links the event to a key. Neither proves that a camera or microphone saw the claimed real-world event. Hardware attestation can be an additional signal if the device supports it, not a replacement for source review.

## Recall profile

The query profile may combine category signals. A broad transcript request must not be demoted to a shallow `knowledge_update` because it also says “current.” Use the deepest applicable retrieval budget, preserve source IDs through compression, and retain the original transcript as an immutable source when the user supplies it. Heat changes ranking and staging; it does not authorize deletion or rewriting.

Acoustic breath/noise features may support opt-in delivery tuning (for example, avoiding an artificial breath cue), but do not retain or compare those features across people as identity markers. Synthetic laughter should be generated by the selected speech model, never pasted from an identifiable human recording.

## Current implementation boundary

The Mr Calendar integration currently records the SHA-256 of the curated `WORKSPACE-MAP.md` and each indexed section. It does not yet create actor keys, signatures, event chains, camera-frame provenance, or a full-chat transcript archive. Arc has no live full-duplex voice service in this checkout. Those are explicit future components, not capabilities implied by the local hash fields.
